## 依存グラフ

```
            ┌─ 01 fixtures ──────────────────────────┐
            ├─ 02 loader ─────┐                      │
            ├─ 03 store ──────┤                      │
            ├─ 04 parser ─────┤                      │
00 基盤 ────┼─ 05 edit ───────┤                      │
            ├─ 06 comments ───┼── 12 統合 ── 13 E2E ─┘
            ├─ 07 preview ────┤
            ├─ 08 inject ─────┤
            ├─ 09 ui-layer ───┤
            ├─ 10 ui-editor ──┤
            └─ 11 ui-comments ┘
```

- **Wave 0**: 00 を最初に 1 人で終わらせる。ここで型・メッセージ・依存パッケージ・ディレクトリを決める
- **Wave 1**: 01〜11 は互いに依存しないので同時に着手できる
- **Wave 2**: 12 は Wave 1 がすべて承認されてから着手する
- **Wave 3**: 13 は 12 の承認後に着手する

## 並列開発のルール

1. **担当ディレクトリの外は変更しない**。とくに次の 3 つは 00 以外で変更しない
   - `src/shared/`（共有の型・定数）
   - `package.json` / `pnpm-lock.yaml`（依存パッケージ）
   - ルートの設定ファイル（`tsconfig*.json`, `vite.config.ts`, `vitest.config.ts`, `playwright.config.ts`, `eslint.config.js`, `.prettierrc`）
2. 共有の型や依存パッケージの追加が必要になったら、作業を止めてチケットの「メモ」欄に書き、まとめて 00 の担当（または統合担当）が `src/shared/` に反映する
3. 他の層の実装を `import` しない。他層とのやり取りは `src/shared/` の型だけを使い、テストではモックを使う。実物どうしの配線は 12 で行う
4. 単体テストは対象ファイルの隣に `*.test.ts(x)` として置く
5. 並列作業は git worktree を使う前提。現在このフォルダは git リポジトリではないため、着手前に `git init` と初回コミットを済ませておく

## 作業の流れ

1. チケットを読み、「関連する設計ルール」と `src/shared/` の契約を確認する
2. 実装しながら「実装チェックリスト」「テストチェックリスト」に `[x]` を付ける
3. 「完了条件」のコマンドがすべて通ることを自分で確認する
4. `reviewer` エージェントにレビューを依頼する（例: 「reviewer で tickets/04 をレビューして」）
5. レビュー欄が「要修正」なら指摘に対応し、もう一度レビューを依頼する。「承認」で完了

## チケットの書式

各チケットは次の節を持つ。

- 冒頭: Wave / 依存 / 担当ディレクトリ / 変更禁止の領域
- 目的
- 関連する設計ルール（`CLAUDE.md` / `.claude/rules/testing.md` から）
- 実装チェックリスト
- テストチェックリスト
- 完了条件
- メモ（作業中の気づき・共有契約の変更依頼）
- レビュー（`reviewer` エージェントが記入）
